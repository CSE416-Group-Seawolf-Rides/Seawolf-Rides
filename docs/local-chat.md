# Local demo chat

The existing conversation/bubble UI now has a real shared Inbox. This remains **demo-seawolf-rides emulators only**: no cloud Functions deployment, billing, or external messaging service.

## Demonstration

1. Stop backend/Expo and wait for emulator export before pulling the updated PR branch. Restart the usual local backend (`--traffic-eta` with the private TomTom environment, or `--live-osrm`) and Expo launchers. Both clients must use the same Mac LAN host/demo project and persisted emulator dataset. Restarting the backend also loads the new callables and Firestore rules.
2. Rider or driver selects an inbound date, finds a real potential match, and taps **Send chat** on that person's card or View more sheet. No ride request or acceptance is required to chat; vehicle completion is still required for driving requests/acceptance, not conversation.
3. Alternatively, open **View more**, review the proposed times, and tap **Send request**. Only after successful persistence, the match sheet closes and opens the same conversation in Inbox. The recipient can see this conversation before either person sends a text. Requests from drivers and riders behave identically; there is no simulated acceptance or automatic chat message.
4. The conversation opens with the other person's real saved first name. **Start the conversation!** is faint display-only text for an empty chat. It disappears as soon as either participant's first message arrives, and is never stored or sent. Enter a message and tap **Send**; the other account opens Inbox and replies. Both screens stream persisted messages.
5. A compact existing-style card shows **Match inquiry** before a request, or who sent the request and its current Pending/Accepted/Declined/Cancelled status. It includes only the date, campus stop, pickup and arrival times. The trip card remains after messaging; only the empty-chat prompt disappears. Tap **View match** to open the bottom detail sheet (your pin, their approximate area, proposed departure/pickup/arrival) and send a request after reviewing a freshly evaluated plan. Once a request exists, **View request** opens its persisted proposal: the recipient gets **Accept request / Decline request**, the sender gets **Cancel request**, and confirmed rides get the existing accepted pickup/route map. Closing the sheet keeps the chat and draft in place. Tap the header avatar/name for a small profile sheet with the saved name/avatar and this same context. Profiles currently have no saved photo field; the existing initials avatar is used rather than a synthetic profile photo.
6. Return to Inbox to reopen it. An empty inquiry stays out of Inbox until the first message; a request-linked conversation appears immediately for both participants. Conversations are reused across dates and Driving/Riding/Either arrangements, preserving history. The context card follows the latest newly created request for the pair; an old duplicate send cannot switch it back to an older date. Earlier trip discussions remain in message history, not a list of context cards. Accept/decline in Rides or cancel an outgoing pending request from matches/Rides, and verify the status changes on both chat screens.
7. Stop backend with Ctrl+C and wait for export, restart with the same `.local-demo-data`, then reopen Inbox. Auth accounts, conversations, and messages return through the existing export/import process. Signing out or reinstalling Expo does not delete the shared backend history.

Chat does not reserve a seat, accept a ride, change saved schedule/times, or automatically share exact pickup coordinates. A street address typed by a participant is their message; the application does not insert private locations. Confirming or changing a ride still requires the supported ride actions.

## API and access

- `startMatchChat({driverId,riderId,driverRevision,riderRevision,localDate})`: verified campus caller must be one of two different participants. New conversations reuse `prepareCalendarPair()` and the canonical evaluator, current eligibility/discovery/schedule/revisions, and the shared bounded routing scheduler/cache. A transaction rechecks the prepared input snapshots before creating the thread. Infeasible, unknown, opted-out, or changed inputs cannot create a new conversation. No alternative compatibility evaluator is added.
- Threads use a hash of sorted participant IDs: simultaneous/crossed starts reuse one conversation. Existing conversations can be reopened after commute changes or acceptance without rerouting. Both accounts must remain eligible to initiate or send; opting out of future matching does not delete an existing conversation.
- `sendChatMessage({chatId,messageId,text})`: verified participant only, 1–2,000 non-whitespace characters, plain text. Server assigns sender/time and transactionally increasing sequence; client cannot forge another sender. A retained message ID makes retries idempotent. Reusing an ID with different text/sender fails. Retries after navigating away/reloading may use a new ID; check history before resending a message whose outcome was uncertain.
- `getChatMatch({chatId})`: authenticated participant only, with both people/date/arrangement taken from server-owned inquiry context. It refreshes just that pair using current normalized saved inputs/revisions, the same canonical evaluator, and the existing bounded scheduler/cache. It rechecks snapshots after routing. Returns caller-owned exact start plus the other person’s privacy area and current evaluated timing; never the other person’s exact point. Opt-out, commitments, invalid dates, incompatible/unknown routes, changed inputs and busy routing fail closed. A legacy inquiry without structured trip context cannot supply a reviewed proposal; send a current reviewed request from the calendar to link its trip context. The sheet uses the conversation’s current dated arrangement; choose another date/arrangement from the calendar.
- Opening an inquiry sheet refreshes once; subsequent refreshes are explicit, with no polling or automatic retry. Only a current reviewed match can enable **Send request** (traffic forecasts expire after two minutes; past departures cannot be sent). Opening a request sheet reads its persisted proposal without routing. Chat actions reuse `createRideRequest`, `respondToRideRequest`, and `cancelRideRequest`, including vehicle completion, strict timing/revision revalidation, attempt IDs, atomic seats/commitments and participant authorization. A failed acceptance does not silently change the displayed proposal; the sender can cancel and refresh. Expired incoming requests have no acceptance control. Declined requests remain final. After cancellation, Refresh match can prepare a new proposal.
- `createRideRequest` atomically creates/links the pair's conversation with the request, returns `chatId`, and preserves existing messages. No extra routing is needed to open that chat after request creation. Legacy duplicate requests can backfill a missing thread. Concurrent inquiry/request creation and crossed requests share the same conversation ID. The linked request is read through its existing participant-only rules, so status updates do not rely on a duplicate status stored in chat.
- `/chats/{id}` contains participant IDs/names, compact dated trip timing/campus context, optional linked request ID, last-message summary, count, and server times. `/chats/{id}/messages/{messageId}` contains sender/text/time/sequence. Neither contains matching inputs or exact coordinates. Verified participants alone can read; all client writes are denied. Messages and summaries are written only by the local trusted backend.
- Inbox queries constrain `participantIds` to the signed-in UID. Conversations listen to the latest 50 messages in sequence order; **Load earlier messages** expands history by 50. Sequence ordering remains deterministic when two users send simultaneously. Errors retain the draft and permit retry; this is not an offline send queue.

Push notifications, unread badges/read receipts, attachments, blocking/reporting, message deletion, and chat-driven trip amendments are not part of this demonstration. Both clients must connect to the local backend to receive live updates.

## Verification

The two-account fake-router emulator suite checks pre-request creation, self/third-party/stale/incompatible/opted-out rejection, crossed starts, inquiry-to-request reuse without message loss, request-only Inbox entries for both accounts, live pending/accepted/declined/cancelled context reads, participant-only inquiry refresh with caller-only exact coordinates, fresh revisions after edits, opt-out rejection and shared routing ownership, stale duplicate context protection, real-time delivery to both accounts, concurrent sequencing, duplicate retries, participant-only reads/actions, denied direct writes, Inbox queries, and no routing calls when messaging. The export/import check re-authenticates both users and reads the persisted conversations (including a request with no text), linked requests and ordered messages after a backend restart. Cloud resources and the user's actual demo dataset are not used by these tests. Physical-device keyboard/profile-sheet layout, match-sheet dismissal and navigation after Send chat/Send request, View match/View request sheet actions, disappearance of the empty-chat prompt, and live delivery on two devices still require the manual walkthrough above.
